## Context

应用是单用户桌面程序,原先用 SQLite 单文件。改用 MySQL 后,应用依赖一个独立运行的服务。

## Decisions

1. **驱动:`mysql` crate(同步)。** 现有业务代码是同步的,工具调用也在阻塞线程里执行,同步驱动改动最小;默认不带 TLS,本机回环连接不需要。
2. **连接池按需创建。** 应用状态里保存 `Option<Pool>`,每次命令取用时若尚未连接就尝试连接。这样 MySQL 晚于应用启动、或中途重启后,无需重启应用即可恢复。
3. **连接配置:`database.json` 或 `LEDGER_DB_URL`。** 密码不进代码库、不进界面;配置文件权限 600。界面只显示不含密码的连接描述。
4. **专用最小权限账号。** 账号 `ledger` 只拥有 `ledger` 库,以及测试用的 `ledger_test_*` 前缀库,不用 root。
5. **日期与月份仍存为文本(`YYYY-MM-DD` / `YYYY-MM`)。** 业务逻辑大量按字符串比较和截取,保持不变,避免引入时区与类型转换风险。
6. **估值表加唯一键 `(account_id, date)`。** 同日重估改为 `ON DUPLICATE KEY UPDATE`,原先"先删后插"在并发下不是原子的。
7. **多步写入放进事务。** 新建账户(账户 + 初始估值)、设置预算(先删后插,因为 `UNIQUE` 对 NULL 不生效)、保存设置(多个键)。
8. **备份改为 JSON 导出。** MySQL 没有"复制一个文件"的等价物;依赖 `mysqldump` 会要求用户机器上额外安装工具。应用内导出读取所有表,使用一致性快照,不会读到写了一半的数据。恢复在单个事务内"清空再写入",校验失败或中途出错都整体回滚。
9. **数字列用预编译协议读取。** 文本协议会把所有数字当字符串返回,备份里的金额会带引号。
10. **旧数据迁移做成 example 而非应用功能。** 这是一次性需求;`rusqlite` 因此只是开发依赖,应用本体不含 SQLite。工具只在目标库为空时导入,只读打开源文件。
11. **测试直连真实 MySQL。** 每个用例建独立临时库,Drop 时删除。这样 SQL 方言差异(子查询、upsert、事务)都被真实验证,而不是被模拟掩盖。

## Risks / Trade-offs

- 应用现在依赖一个常驻服务:未启动时无法使用(界面会提示原因)。已通过 `brew services` 设为登录自启。
- 体积与资源:MySQL 本体约 330 MB,常驻内存数百 MB,与"体积小"的初衷有取舍;这是改用独立数据库的代价。
- Homebrew 默认 root 无密码(仅监听 127.0.0.1)。同机其他进程可用 root 访问全部数据库;建议运行 `mysql_secure_installation` 设置 root 密码。
- 备份文件未加密。
- 旧的 SQLite 备份(`.db`)不能直接在应用里恢复,需先用导入工具迁入。
