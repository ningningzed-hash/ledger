## Context

`agent.rs` 已有完整的工具循环(最多 6 轮、`role:"tool"` 回填、错误以文本返回让模型自行纠正)和单月粒度的读工具。账目存于 `txn`(`date` 为 `YYYY-MM-DD` 字符串,`amount` 为正整数"分",`kind` 区分 expense/income),分类、账户可空。`report.rs` 已经提供月份加减、月末、`earliest_month`,`core::net_worth_as_of` 可回看任意日期的净资产,`core::category_summary_range` 支持月份区间。缺的是:日期级区间、多条件筛选、分组统计的均值/中位数、期间对比和异常识别。

## Goals / Non-Goals

**Goals:**
- 模型能回答跨月、跨分类、带筛选条件的数据问题,且所有数字由程序算出。
- 每个工具返回体有上限,单次调用不会撑爆上下文。
- 全部只读;参数错误时返回可纠正的提示。

**Non-Goals:**
- 任意 SQL 或表达式查询。
- 预测、回归、季节性分解等高级分析(只做描述性统计与对比)。
- 前端图表或新页面。
- 多币种换算(与总览一致,直接相加,是已知限制)。

## Decisions

1. **结构化工具,不开放 SQL。** 候选是"一个只读 SQL 工具"。它灵活,但 14B 模型写 SQL 容易出错、需要把表结构塞进提示词,还要防越权读 `setting` 里的 API Key、写入语句和慢查询。结构化工具的参数少、校验明确,金额口径(分→元、`未分类`归并)由程序保证一致。代价是新需求要加工具,可接受。

2. **统计在 Rust 里算,用整数分。** 合计与笔数在 SQL 中聚合;中位数与均值在内存中对该组金额排序后计算,均值四舍五入到分,中位数偶数个时取中间两个的平均并四舍五入。出口统一转"元"。中位数不用 MySQL 窗口函数,避免依赖版本且便于单元测试。

3. **统一筛选结构 `Filter`。** 字段:`from`/`to`(`YYYY-MM-DD`,含两端)、`kind`、`category`、`account`、`keyword`、`min_amount`/`max_amount`(元)。`query_transactions` 与 `aggregate_transactions` 共用同一个构造函数,生成带占位符的 WHERE 和参数列表,杜绝字符串拼接。`keyword` 同时匹配备注和分类名,并转义 `%`、`_`、`\`。分类/账户名沿用 `find_category`/`find_account` 的解析,找不到时返回可选项列表(与 `add_transaction` 一致)。

4. **区间默认值与校验。** 省略 `from`/`to` 时默认最近 90 天(到今天);`from > to` 报错;跨度超过 10 年报错。日期按 `NaiveDate` 解析,拒绝 `2026-02-30` 之类的非法日期。

5. **分组键。**（每次只统计一种类型,`kind` 默认支出;区间内第一个月没有可比的上月,环比为 `null`;区间首尾不是整月的月份带 `partial` 标记。） `month` → `YYYY-MM`;`week` → 该周周一的日期(ISO 周,周一起);`category` → 分类名,无分类归"未分类";`account` → 账户名,无账户归"无账户"。按时间分组时按时间正序,按分类/账户分组时按合计降序。环比仅在 `month` 分组时计算,= (本月-上月)/上月,上月为 0 时置 `null`,中间缺失的月份补零组,保证"上月"就是日历上的上个月。

6. **返回体大小上限。**

   | 工具 | 上限 |
   |---|---|
   | `query_transactions` | `limit` 默认 30、最大 100;`offset` 分页 |
   | `aggregate_transactions` | 最多 60 组,超出保留最近/最大的 60 组 |
   | `cash_flow_trend` / `net_worth_trend` | `months` 默认 6、最大 36 |
   | `compare_periods` | 分类差额最多 15 行,其余合并为"其他分类" |
   | `find_outliers` | 最多 10 笔 |

   任何被截断的结果都带 `truncated: true` 与 `total`(总数),模型据此决定是否缩小范围再查。

7. **趋势复用 `report::report`。**均值与最高/最低月只统计已过完的月份,当前月标 `partial` 且不计入,避免月中的半个月拉低均值。 `cash_flow_trend` 与 `net_worth_trend` 调用现有的 `report()`,保证与报表页口径一致(区间不早于最早数据、当前月净资产取当前值)。在其上补充储蓄率(结余÷收入,无收入为 `null`)、均值、最高/最低月份、净资产变化量与幅度。

8. **异常支出的定义。** 对区间内每个分类的支出,取该分类的中位数 M;单笔金额 ≥ `max(factor × M, min_amount)` 记为异常,`factor` 默认 3、`min_amount` 默认 100 元。样本少于 5 笔的分类不判定(中位数不稳定)。按 `amount ÷ M` 的倍数降序返回。选用中位数而非均值+标准差,是因为小样本里一笔大额就会把均值和方差一起拉高,把自己"藏"起来。订阅类固定支出(如房租)金额稳定,中位数等于其本身,不会被判为异常。

9. **工具循环提高到 8 轮。** 典型的分析是"趋势 → 下钻某分类 → 查明细 → 回答",已经是 3~4 轮,加上写操作前的查询容易触顶 6 轮。仍保留上限;超过时沿用现有逻辑(返回已有文本或提示)。

10. **提示词规则。** `rules.md` 追加:涉及合计、均值、占比、增减、排名的问题必须调用分析工具,不得自己加减;回答要写明统计区间和关键数字;数据不足(笔数很少、区间很短)时要说明结论不可靠;不得把描述性统计说成预测。保留既有"不透露工具内部名称"。

11. **既有工具保持不变。** `list_transactions`、`category_summary`、`get_overview` 行为不改,避免破坏已有的对话和测试;新工具描述里写明何时用哪个(单月概览用旧的,跨月/带条件用新的)。

## Risks / Trade-offs

- **工具数从 9 增至 15**,小模型选错工具的概率上升 → 描述里用"适用场景 / 不适用场景"区分,并加真实模型冒烟测试(`live_` 前缀,默认忽略)。
- **模型仍可能忽略规则自己心算** → 规则明确 + 工具返回里直接带好 `total`、`avg`、`change_pct` 等现成数字,降低心算的诱因;冒烟测试检查数字与程序结果一致。
- **中位数与均值在内存里算**,单个区间命中十万笔时内存与耗时上升 → 10 年上限 + 个人账本量级(每月百笔)下可忽略;若以后变大再改成 SQL 侧聚合。
- **关键词用 `LIKE '%…%'` 无法走索引** → 同上,量级可接受;`date` 区间条件先收窄。
- **异常检测是启发式**,会漏判/误判 → 返回倍数和该分类中位数,让模型如实表述为"明显高于常规",而不是下结论。
- **周分组用周一起始**,与部分用户习惯(周日起)不同 → 返回每组的起始日期,表达上不会产生歧义。
